# Распределённый режим OpenCode: первая рабочая версия DAEP

Актуальная постановка владельца: 10 сентября 2026 года.
Статус: требования к реализации, не свидетельство работающего runtime или live acceptance.

## 1. Продуктовый результат и граница scope

Пользователь работает в любом своём Git-проекте через OpenCode на DevCoveer и явно указывает: выполнить задачу распределённо в Kaggle. Основная модель декомпозирует задачу, вызывает DAEP для выполнения независимых coding-подзадач в отдельных notebooks, наблюдает результаты, объединяет изменения и запускает сквозные проверки на инфраструктуре проекта. При необходимости готовит фактический пакет для исправлений непосредственно в ChatGPT.

Первая версия: только Kaggle, 1–4 одновременно используемых DAEP notebooks в общем пуле; внутри задачи может быть больше последовательных подзадач. Число workers задаётся вручную либо выбирается автоматически. Другие backend-адаптеры, MCP-вход, перенос dataset-loop и автоматическая починка самого DAEP — позднее, не условия первого запуска.

Классификация исходников, запреты передачи кода моделям, DLP и согласования провайдера по классу данных НЕ входят в проект. Выбор моделей не блокируется таким механизмом. Остаётся обычная техническая гигиена: credentials не писать в Git/логи, чужие задачи не останавливать, пользовательскую рабочую директорию не перезаписывать.

Это репозиторий программного инструмента, не исследовательский датасет. Не создавать собственный CI/CD, UI-платформу, универсальный workflow engine, распределённую БД или обязательный многоагентный комитет на каждую задачу.

## 2. Явный вход из текущего проекта

Примеры пользовательских инструкций, НЕ уже реализованный синтаксис команды:

```text
Выполни задачу в распределённом режиме на Kaggle.
Ноутбуки: auto, не более 4. Локально — координация, интеграция и сквозные тесты.

Выполни задачу распределённо на Kaggle, используй до 2 ноутбуков.
Результат при блокировке: пакет для продолжения в ChatGPT.
```

Глобальный инструмент/команда OpenCode передаёт DAEP корень текущего worktree, remote, точный base SHA, исходную постановку, критерии завершения и выбранный режим. Не требуется устанавливать копию DAEP в каждый продуктовый репозиторий. Команды подготовки и тестирования берутся из существующей конфигурации проекта; небольшой центральный override допустим.

Режим сохраняется в job. Недоступность Kaggle не разрешает незаметно переключить реализацию всей задачи на локальный OpenCode. Пользователь видит, где реально исполняется работа. Локальные изменения допустимы для конечной интеграции; существенная доработка возвращается в notebook либо в ChatGPT согласно режиму задачи.

Submit быстро возвращает сохранённый job ID. Он не удерживает вызов инструмента до окончания notebook. Предварительная проверка выявляет недоступный репозиторий, отсутствие необходимых credentials, callback URL или невоспроизводимое рабочее состояние до расходования notebook. Незакоммиченные изменения либо включаются в явный checkpoint, либо выдаётся конкретный запрос сохранить их; молча проигнорировать их нельзя.

## 3. Два вида оркестрации, одна небольшая система

| Ответственный | Его работа |
| --- | --- |
| Основная модель OpenCode | Понять задачу; выделить независимые части и зависимости; выбрать модели; оценивать полезный прогресс; менять план; интегрировать и проверять результат; готовить пакет для ChatGPT |
| Детерминированный supervisor DAEP | Учитывать notebooks; резервировать ёмкость; запускать; принимать события; сохранять checkpoints; сверять фактическое состояние; повторять допустимые операции; восстанавливать попытки; подтверждать остановку |
| OpenCode внутри notebook | Реализовать одну назначенную часть; выполнять локальные тесты; передавать фактические изменения, ошибки и результаты |

Supervisor — обычный постоянно работающий код, а не LLM, которую нужно попросить проверить ноутбуки. Он продолжает техническое сопровождение при закрытии окна, завершении сессии или недоступности модели-координатора. План, оригинальная задача, job ID, результаты и решения сохранены вне чата. Возобновляемая coordinator-сессия получает это состояние; новые события не должны запускать несколько координаторов одновременно.

Минимальное размещение: один сервис supervisor на DevCoveer, SQLite, существующее удалённое хранилище для checkpoints/backup, CLI и тонкая глобальная интеграция OpenCode. Никакого active-active кластера для первой версии.

## 4. Параллельность 1–4

Модель определяет полезную параллельность, supervisor — реально доступную ёмкость. Каждая подзадача содержит назначение, base SHA, ожидаемый результат, проверки, зависимости и область изменений. Достаточно списка зависимостей; отдельный DAG-движок не нужен.

`workers=N` задаёт запрошенный верхний предел одновременной работы этой задачи, 1 <= N <= 4. `workers=auto` выбирает предел не выше 4 с учётом независимых готовых подзадач и наблюдаемой ёмкости. В первой версии общий пул DAEP также ограничен четырьмя notebooks, чтобы несколько проектов не раздували потребление незаметно.

Число одновременно назначенных исполнителей ограничивается минимумом: запрошенный предел, готовые независимые подзадачи, доступные ресурсы общего пула и фактические ограничения Kaggle. Если запросили 4, а доступны 2, запускаются две полезные части, остальные явно ожидают ресурс. Не создавать фиктивную параллельность и пустые notebooks ради числа. По мере завершения одного worker можно назначить следующую готовую часть.

Различать резервирование, provider queue и действительно исполняющийся notebook. Показывать `requested`, `reserved`, `queued_at_provider`, `running`, причину меньшего числа и время последнего наблюдения. Четыре — лимит DAEP, не обещание Kaggle предоставить четыре сессии каждому аккаунту.

Учитывать другие jobs DAEP и видимые внешние notebooks, включая dataset-loop. Внешние notebooks только наблюдаются, не останавливаются для освобождения места. Если установленный API не показывает точную свободную ёмкость, сообщать ограниченность наблюдения; использовать собственные leases и поэтапное допущение запусков с обработкой ответа провайдера. Не выдавать число зарегистрированных свободных слотов за все свободные ресурсы аккаунта.

Резервирование атомарно. Повтор submit не резервирует второй комплект. При конфликте/нехватке ресурсов — очередь и автоматическая повторная проверка, не ручное создание notebook.

## 5. Связь с notebook и контроль по ходу

Основной канал: notebook сам устанавливает исходящие HTTPS-запросы к единому supervisor. На DevCoveer нужен один доступный из Kaggle endpoint. HTTP-сервер внутри notebook без маршрута наружу сам по себе не делает notebook доступным извне; публичный адрес/туннель каждому worker не нужен для первой версии.

```text
OpenCode на DevCoveer → DAEP supervisor → Kaggle lifecycle API
                             ↑
                     исходящие HTTPS
                             │
             worker → локальный OpenCode server / JSON events
```

Внутри notebook можно использовать `opencode serve` на loopback с events/session status либо структурированный поток `opencode run`. Worker читает реальные сообщения, вызовы инструментов, результаты тестов и модель сессии, а не сочиняет статус. Наружу передаются нормализованные события и доступные по запросу ограниченные фрагменты вывода. Полная трасса не засыпает основную модель каждым токеном.

Ответ supervisor на heartbeat/long-poll доставляет команды: остановиться, сохранить checkpoint, отдать диагностический фрагмент, принять уточнение. У команды есть ID и подтверждение; повтор доставки не повторяет эффект. События нумеруются и подтверждаются после сохранения. При разрыве связи worker повторяет неполученные события; локальный буфер ограничен. Данные, которые ещё не вышли из погибшего notebook, не объявляются сохранёнными.

Независимо от callback supervisor опрашивает провайдера. Состояние Kaggle и состояние процесса OpenCode не подменяют друг друга: `provider=running` ещё не доказывает, что модель и код продвигаются. Сообщения о существенных переходах доставляются активному coordinator, остальные доступны через status/follow. Этот delivery path тоже требует live-теста.

Job view показывает проект, цель и execution mode; subtasks и модели; фактические notebook refs; текущий этап/ошибку; свежесть heartbeat; последний подтверждённый checkpoint; результаты проверок; автоматическое следующее действие. Процент готовности по числу tool calls не вычисляется.

## 6. Надёжность и честные статусы

Для каждой попытки сохраняются job/subtask/attempt ID, поколение исполнения, provider account, точный kernel ref, revision/run identity, base SHA, время наблюдения, checkpoint и результат. Имя notebook либо статус его latest run недостаточны для привязки результата.

Сбой интернета не позволяет достоверно знать, жив ли удалённый процесс. Требование «без неопределённых статусов» реализуется как отсутствие бесконечного немого `UNKNOWN`: состояние сверки/потери связи явно показывает последнее подтверждённое наблюдение, причину, следующий шаг и срок перехода. Нельзя ради красивого UI выдать неподтверждённое состояние за факт.

| Событие | Автоматическая реакция |
| --- | --- |
| Ответ запуска потерян | Сверить точную попытку с provider и callback; не создавать дубликат вслепую |
| Нет heartbeat, provider отвечает | Проверить состояние попытки и OpenCode; не считать смерть доказанной по одному пропущенному heartbeat |
| Notebook действительно завершился/упал | Взять последний подтверждённый checkpoint; создать новую попытку только этой подзадачи; остальные не перезапускать |
| Модель временно недоступна/429 | Ограниченный backoff либо смена настроенной модели с сохранением состояния |
| Связь с supervisor потеряна | Повторить доставку, локально буферизовать ограниченный объём; по истечении lease перестать создавать новые внешние эффекты |
| Срок notebook подходит к концу | Заранее сохранить состояние и передать продолжение в новую попытку |
| Checkpoint или push не подтверждён | Повторное чтение сохранённого результата; не считать локальный commit внешним backup |
| Пришёл результат старого worker | Сохранить для диагностики, но не применить поверх действующей попытки |
| Пользователь отменил job | Остановить выдачу новых частей; запросить остановку своих workers; отдельно подтвердить фактический stop и сохранность результата |
| Supervisor перезапущен/восстановлен | Прочитать durable state, сверить provider/Git, восстановить наблюдение; не перезапускать всю очередь |
| Повторяется одна непоправимая ошибка | Остановить цикл повторов, сохранить результат и выдать конкретный blocked/handoff с причиной и воспроизводимыми данными |

Каждая операция имеет deadline, классификацию ошибки, предел повторов и next action. Неизвестная новая ошибка попадает в общий диагностируемый failure path, а не роняет весь supervisor и не запускает бесконечный retry. Настройка модели/инфраструктуры не должна требовать от владельца ручного восстановления очереди.

Один контролируемый writer применяет результат каждой подзадачи. Старые попытки могут сохранять собственные артефакты, но не заменять интеграционную ветку. Повторы внешних вызовов не гарантируются exactly-once; повторное принятие результата предотвращается устойчивыми IDs и проверкой текущей попытки.

Нулевая потеря ещё не сохранённых изменений при внезапной гибели машины не обещается. Сохраняется последний подтверждённый checkpoint, показывается возраст несохранённых изменений. Периодические snapshots не зависят от способности модели вспомнить команду сохранения. Экспорт полной OpenCode-сессии и ретроспектива не задерживают доставку кода.

## 7. Модели и исчерпание free usage

Поддержать явный model/provider ID и набор настроенных альтернатив: Zen, NVIDIA, другие OpenCode providers, дополнительные OpenAI GPT-модели для сложных частей/итогового контроля. Не строить отдельный model gateway и классификатор кода. Фактически используемая модель, переключения и причины видны по каждой попытке.

При `free usage exceeded` или эквивалентной ошибке сохранить изменения и состояние, подтвердить checkpoint и передать supervisor причину вместе с запросом продолжения. Не полагаться на завершающий ответ уже недоступной модели: сохранение выполняет worker wrapper.

При необходимости продолжение разворачивается в новом notebook из того же job/subtask checkpoint. Замена notebook сама по себе не обнуляет лимит endpoint/аккаунта: если ограничение общее, продолжение использует доступную настроенную альтернативу или состояние `waiting_for_model` с понятным условием повторной попытки. Не размножать notebooks, которые все получают ту же ошибку.

Правила повторов относятся и к основной модели-координатору. Недоступность координатора не должна уничтожать уже полученные результаты дочерних workers.

## 8. Склейка, сквозное тестирование и ChatGPT

Каждый worker пишет в отдельную task/attempt-ветку либо сохраняет эквивалентный проверяемый patch; не редактирует общую живую checkout пользователя. Coordinator собирает результаты в отдельном integration worktree от известного base SHA и повторно проверяет именно объединённый результат.

Общие интерфейсы определяются до параллельных реализаций. Текстовый Git merge не означает архитектурную совместимость. Если upstream-контракт изменился, зависимая часть помечается требующей перепроверки; при настоящем конфликте coordinator либо делает небольшую интеграционную правку, либо отправляет точечную подзадачу обратно.

Проверки выполняются там, где доступна нужная инфраструктура проекта, через существующие команды/CI. Универсальный разворот любого runtime и production deploy не входят в DAEP v1. Отсутствующая инфраструктура явно отделяется от ошибки кода.

`worker completed`, `result saved`, `integrated`, `tests passed` и `job succeeded` — разные факты. Job успешно завершён только по исходным критериям и проверкам фактического итогового SHA. Подготовленный пакет для ChatGPT — `handoff_ready`, не ложный успех реализации.

Пакет содержит исходную задачу, принятые решения/план, repository/branch/base/result SHA, изменения, точные команды и результаты проверок, оставшиеся ошибки и конкретный запрос на исправление. После внешних правок можно продолжить тот же job с новой версией входа и повторной проверкой, не реконструируя вручную историю notebooks.

## 9. Хранение и сопровождение без раздувания Git

Продуктовые репозитории хранят код, тесты и необходимые изменения документации. Heartbeats, логи, task JSON, архивы сессий, backups и периодические ретроспективы не коммитятся туда. Не делать отдельный Markdown-handoff на каждый внутренний переход.

Checkpoints: подтверждённые commits с кодом либо snapshots/patches в существующем внешнем хранилище. Ветка результата остаётся компактной; не сохранять в Git бинарные дампы среды. Runtime state живёт вне checkout DAEP. Один машиночитаемый итог задачи формируется автоматически из тех же событий; развёрнутый export — по запросу.

Supervisor запускается как автоматически перезапускаемый сервис. Для SQLite/конфигурации нужен согласованный backup вне той же машины; checkpoints тоже должны переживать её потерю. Проверка restore входит в приёмку. Отказ одного сервера может временно приостановить работу, но не требует ручного воссоздания списка задач и не разрешает двойное применение результата.

## 10. Первая source-задача и приёмка

Реализовать один сквозной путь: OpenCode текущего проекта → явный distributed submit → два независимых Kaggle OpenCode workers → наблюдение и подтверждённые checkpoints → возврат изменений → интеграция → реальные проверки → итог. Одна coordinator-модель плюс supervisor; без обязательного planner/reviewer/fixer-конвейера. Поддержку лимита 1–4 заложить сразу.

Параллельно использовать тестовый provider для воспроизводимых сбоев, но не выдавать его за live Kaggle acceptance. Реальный запуск двух notebooks должен иметь пересекающиеся интервалы исполнения, а не два последовательных запуска под названием parallel.

Минимальная приёмка:

1. Две реальные coding-подзадачи выполняются параллельно, события видны до завершения, результат обеих сохранён и объединён; сквозные проверки подтверждены.
2. Потеря одного notebook вызывает восстановление его подзадачи с checkpoint; второй не перезапускается. Старый результат не заменяет новый.
3. Повтор submit, потерянное подтверждение launch/push, повтор события/команды, лимит модели, разрыв callback и перезапуск supervisor не создают неконтролируемых дублей и зависших jobs.
4. Ручные 1–4 и auto корректно учитывают общий пул и внешнюю занятость. Реальная недоступность четырёх ресурсов отображается как ожидание, не как фиктивный успех теста четырёх notebooks.
5. Тот же путь работает в другом проекте без изменения ядра. Готовится пригодный для продолжения в ChatGPT пакет; никаких служебных трасс в продуктовом Git.
6. Backup восстанавливается в чистом окружении; provider/checkpoints сверяются, продолжение не требует вручную составлять очередь заново.

Не мигрировать dataset-loop и не делать альтернативный backend обязательными до этой приёмки. Не объявлять работающую схему по README, unit-тестам, одному успешному bootstrap или одной зелёной дочерней задаче.
