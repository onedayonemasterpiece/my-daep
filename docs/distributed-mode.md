# my-daep v1 — итоговый проект распределённого режима OpenCode

Обновлено: 2026-09-10. Это согласованная по требованиям владельца постановка, а не заявление о работающем runtime. Порядок реализации и передачи в новое окно: [implementation-task.md](implementation-task.md). Прежние варианты этого документа заменены; история остаётся в Git.

## 1. Продуктовый контракт

Пользователь работает в существующем GitHub-проекте через OpenCode на DevCoveer и явно указывает: «выполни распределённо на Kaggle, workers=auto или 1–4». Основная модель декомпозирует задачу, отправляет независимые coding-части в отдельные OpenCode внутри Kaggle, следит за содержательным прогрессом, объединяет изменения и проводит сквозные проверки на доступной инфраструктуре проекта. Существенные исправления возвращаются в workers либо оформляются для непосредственной работы ChatGPT через GitHub.

Распределённый режим считается начатым только после сохранения job и выдачи пользователю job ID, repo/base SHA, запрошенного лимита и фактического backend. Одного обещания модели «сделаю распределённо» недостаточно. Глобальная команда `/daep` — явный вход; обычная инструкция в диалоге вызывает тот же инструмент. Недоступность Kaggle не даёт права молча заменить распределённую разработку локальной.

Первая версия: один управляющий сервер, только Kaggle, до четырёх одновременно занятых DAEP notebooks во всём пуле, одна GitHub-репозитория на job. Количество последовательных подзадач может быть больше четырёх. Разные jobs могут относиться к разным проектам.

В scope НЕ входят классификация кода, DLP, запреты передачи моделям, собственный LLM gateway, универсальный CI/CD, Kubernetes/Redis/брокер сообщений, отдельный frontend, новый публичный MCP/OAuth, другие вычислительные backend, миграция dataset-loop и автоматическое самоизменение DAEP. Нет обязательного комитета planner/reviewer/fixer. Секреты не коммитятся и не печатаются — обычная техническая гигиена, не новый продукт.

## 2. Минимальная архитектура и владельцы состояния

```text
Пользователь / существующий проект
                ↓
OpenCode на DevCoveer: план, интеграция, сквозные проверки
                ↕ глобальный tool / CLI
DAEP supervisor на DevCoveer: SQLite, lifecycle, GitHub App broker
                ↕ Kaggle API + исходящий HTTPS от workers
       1–4 Kaggle notebooks: wrapper + OpenCode
                ↕ clone / fetch / checkpoint / push
GitHub целевого проекта: исходники → attempt-ветки → integration-ветка → один PR
                ↓
       существующий CI и инфраструктура проекта
```

GitHub обязателен: это источник кода и внешняя сохранность изменений. SQLite — источник состояния задач, попыток, плана и управления; GitHub не используется как живая очередь/шина heartbeat. Полные логи и согласованные backup базы хранятся вне продуктового Git, в существующем внешнем хранилище. Для кода v1 достаточно Git checkpoints; второй обязательный patch/object publisher не строить.

Основная модель определяет смысл задачи, независимость частей, модели, дальнейшие исправления и достаточность результата. Детерминированный supervisor учитывает ресурсы, запускает и восстанавливает попытки, принимает события, проверяет сохранность и ограничения. Worker wrapper отвечает за процесс OpenCode, heartbeat, периодические checkpoints и реакцию на потерю модели/связи. Эти обязанности не перекладываются на память LLM.

Реализация: один Python-пакет/сервис с CLI, SQLite и небольшим TypeScript/JavaScript tool/plugin для глобального OpenCode. Использовать уже применяемые Python/FastAPI/Git-инструменты; не выделять token broker, publisher, ретроспективу и scheduler в отдельные сервисы.

## 3. GitHub: конкретный путь исходников и результата

Job содержит `repository_id`, `owner/repo`, точный `base_sha`, целевую base-ветку, исходную задачу, критерии приёмки, execution mode и сохранённый план. Не предполагать `main`: у my-daep default branch — `master`. Remote и Git-корень определяются из текущего проекта, installation access проверяется до запуска notebook.

У каждой попытки своя ветка:

```text
daep/work/<job-id>/<task-id>/a<attempt>
daep/result/<job-id>
```

Worker получает точный SHA и пишет только свою attempt-ветку по протоколу обвязки. Supervisor проверяет фактический remote commit, родство с ожидаемой базой и принадлежность действующей попытке. Возобновление создаёт новую attempt-ветку от последнего подтверждённого checkpoint. Старую ветку не переиспользовать; поздние commits не подменяют принятый результат.

Основной OpenCode интегрирует выбранные точные commits в отдельном worktree и публикует `daep/result/<job-id>`. Одна исходная задача — не более одного итогового PR, который обновляется, а не пересоздаётся на каждый retry. Промежуточным notebooks PR не нужен. Повтор создания PR после потерянного ответа сначала ищет существующий по repo/head/base. Merge в default branch и production rollout не являются скрытым следствием push или worker success.

Не менять живую checkout пользователя. Незакоммиченные изменения не игнорировать: v1 работает от явного подготовленного Git checkpoint. Если требуется сохранить текущие изменения, инструмент делает понятный отдельный снимок выбранных исходников без смены пользовательской ветки либо сообщает точную необходимость checkpoint; не ставить отсутствующие файлы на удалённое исполнение.

Код, тесты и нужная документация сохраняются в Git. Локальный commit не считается внешним checkpoint до успешного push и независимого readback. Если push завершился, а подтверждение потеряно, проверяется точный ref/SHA, а не делается force-push. Ошибка экспорта сессии не отменяет уже сохранённый код.

## 4. GitHub App и ключи — явное решение v1

Для пилота можно переиспользовать существующую GitHub App, применяемую dataset-loop, и создать у неё отдельный PEM-ключ для DAEP. Новый ключ даёт отдельную ротацию, но НЕ отдельную App identity, отдельные permissions или независимую квоту. Новый key не требуется для каждого проекта или notebook.

Не делать отдельную App обязательным условием source-разработки. Та же реализация должна принимать отдельную DAEP App простой заменой конфигурации. Если рабочая App dataset-loop должна остаться неизменной, использовать отдельную App с перечисленными ниже permissions вместо изменений чужого разворота. Выбор — параметр подключения, не две реализации авторизации. Фактические installations, permissions и server key readiness ещё не проверены; чтение исходников их не доказывает.

Настройки supervisor:

```text
DAEP_GITHUB_APP_ID
DAEP_GITHUB_INSTALLATION_ID
DAEP_GITHUB_APP_PRIVATE_KEY_FILE
DAEP_GITHUB_APP_CLIENT_ID   # только если выбранный JWT-код использует Client ID
```

App ID, Client ID и Installation ID — разные значения. PEM хранится только на управляющем сервере с доступом владельца процесса; credentials dataset-loop не перемещать, не отзывать и не перезаписывать. При повторном использовании App она должна быть установлена на нужные целевые репозитории. Публичность my-daep не создаёт право записи ни в него, ни в другие проекты.

Базовый набор repository permissions:

| Permission | Уровень | Назначение |
| --- | --- | --- |
| Metadata | Read | Идентичность репозитория |
| Contents | Read/write | Clone/fetch, commits и ветки |
| Pull requests | Read/write | Один итоговый PR и его обновление |
| Actions | Read | Состояния и логи существующих workflow runs |
| Checks | Read | Результаты check runs |
| Commit statuses | Read | Legacy commit statuses, если проект ими пользуется |

Не нужны webhook, Issues/Projects/Administration и свой GitHub Actions runner для самого DAEP. Actions write нужен только при явно используемом workflow_dispatch/rerun/cancel; Workflows write — при задаче, меняющей `.github/workflows`. Отсутствие такой реальной capability должно называться точно, не маскироваться под ошибку модели. Не выдавать эти права за уже настроенные.

PEM → короткий App JWT → installation token — работа локального broker внутри DAEP. Worker получает installation token, ограниченный целевым repository и необходимыми правами, через существующий исходящий канал с attempt credential. Repo/installation берутся из сохранённого job, не из произвольного аргумента worker.

GitHub installation tokens истекают через час. Git credential helper получает/обновляет токен до Git-операций по `expires_at` с запасом; временный cache — только в защищённом runtime, не в Git URL, task JSON, prompts или постоянных логах. После 401 допускается один refresh и повтор после сверки результата; отсутствие permission/отозванная installation не лечатся бесконечным refresh. Старой попытке не выдаются новые credentials. Токен — opaque string: не предполагать фиксированные длину, префикс или формат.

Важно: GitHub token ограничивается репозиторием и permissions, а не одной веткой. Именование веток — протокол против случайных конфликтов, не криптографическая изоляция. Fencing DAEP защищает ПРИНЯТИЕ результата и выдачу новых полномочий. Уже выданный токен старого worker может оставаться действительным до отзыва/истечения; гарантии этого ограничения нельзя скрывать. Для v1 не строить ради этого отдельный git-proxy или policy-систему.

Существующий broker dataset-loop и endpoint обновления можно переиспользовать как source-компоненты с тестами, но DAEP не должен зависеть от работающего dataset-loop MCP для каждого mint. Если используется общая App/installation, учитывать общие API-ограничения: bounded cache, backoff и чтение retry/rate-limit headers вместо mint на каждом heartbeat.

## 5. OpenCode-координатор: полный цикл, а не запуск с забытым результатом

Один глобальный вход из любого проекта, без копирования runtime в продуктовые репозитории. Тонкие операции инструмента: submit/plan, status/follow, update/resume, cancel, export. Все они обращаются к одному supervisor. `/daep` — удобная команда над тем же интерфейсом; автоматическое перехватывание всех native Task не требуется.

План — простой список подзадач и зависимостей, не новый workflow DSL. Каждая часть содержит цель, точную базу, ожидаемые изменения/контракт, проверки, зависимости и модель. При зависимости от результата предшественника следующий worker получает его проверенный commit, а не исходный base без сделанных изменений. Изменение общего интерфейса инвалидирует затронутые downstream-проверки.

Обязателен работающий возврат: события окончания/блокировки должны пробуждать или продолжать coordinator-сессию, когда она может обработать следующий шаг. Использовать проверенный SDK/server путь OpenCode (`prompt_async`, session status/messages/events), сериализуя ход одной coordinator-сессии. Сначала читать состояние; не запускать новую координаторскую задачу на каждый heartbeat и не дублировать prompt после потерянного ответа вслепую.

Держать управляемый OpenCode server независимо от подключённой TUI либо иметь проверенный reattach/resume. Закрытие пользовательского окна не должно остановить supervisor и потерять интеграционную очередь. Исходная задача, план, решения, version, session ID и прочитанный event cursor хранятся вне чата; при утрате сессии coordinator восстанавливается из этого пакета. Если coordinator-модель недоступна, workers и сохранённые результаты остаются под контролем, а job явно ожидает модель. Не утверждать автономную интеграцию, если реализован только status polling.

После ручных правок ChatGPT или владельца supervisor принимает новую версию входа и точный SHA, инвалидирует только затронутые результаты и продолжает тот же job. Автоматический rebase на произвольно изменившуюся base-ветку без повторных проверок запрещён протоколом корректности.

## 6. Kaggle и планирование 1–4

`workers=N` — верхний предел для job, `workers=auto` — выбор не выше четырёх. Общий пул DAEP также не превышает четырёх. Число запускаемых частей — минимум из полезно независимых ready tasks, лимита job, свободной ёмкости DAEP и наблюдаемых ограничений Kaggle. Если запрошены четыре, а доступны два, работать двумя и явно ожидать остальные. Не создавать пустые notebooks ради числа.

Один запуск закрепляется за account/kernel/ref, точной provider revision и attempt identity. Резервация сохраняется до внешнего launch; повтор submit с тем же ключом не создаёт job/ресурсы заново, изменение параметров с тем же ключом — конкретный конфликт. После неизвестного результата launch сначала reconciliation по provider и callback, а не слепой повтор `kernels push`.

Показывать requested, reserved, queued_at_provider и running отдельно. Локально свободный слот не доказывает свободную квоту аккаунта. Наблюдать видимые внешние notebooks, включая dataset-loop, без их изменения. Если API не даёт полную ёмкость, указывать свежесть/полноту наблюдения, запускать поэтапно и обрабатывать capacity response; не выдумывать четыре доступных ресурса.

Между проектами простая справедливая очередь ready tasks; завершение части освобождает слот, не требуется повторно стартовать весь job. Для удалённого inference notebook обычно нужен CPU, не GPU; выбранный resource type должен фиксироваться явно.

Повторно использовать конкретный Kaggle transport и bootstrap из dataset-loop, включая уже работающую доставку bootstrap credentials. Не копировать его dataset-specific permissions/candidate contracts. Credentials к моделям и attempt callback не встраивать в публичный notebook; предпочесть уже проверенный механизм Secrets/закрытого bootstrap. Его фактическую работоспособность проверить в live, не считать название функции доказательством.

## 7. Сохранение и телеметрия

Wrapper запускает закреплённую версию OpenCode и читает реальные события локального server/CLI. Notebook устанавливает исходящий HTTPS к единому supervisor на DevCoveer: heartbeat/events/results, ответные команды через ответ/long-poll. Публичный HTTP-порт/туннель каждому notebook не нужен. Supervisor отдельно опрашивает Kaggle: provider running не доказывает прогресс модели.

Event и command имеют attempt identity и последовательный номер/ID. ACK выдаётся после durable записи, дубликат не повторяет эффект. При сетевом сбое ограниченный локальный буфер повторно доставляется; вывод без внешнего ACK может быть потерян вместе с notebook. Не обещать восстановить недоставленную трассу.

Checkpoint делает wrapper на завершённых этапах и периодически при наличии изменений, не LLM по памяти. Использовать согласованный снимок исходников на границе записи с bounded retry; не менять Git index модели в середине её команды. Синтаксически незавершённый код может быть WIP checkpoint, но не verified result. Не ждать зелёных тестов, полного session export или ретроспективы, чтобы сохранить полезную работу.

Начальные настраиваемые ориентиры: heartbeat около 20 секунд, code checkpoint каждые 2–5 минут при изменениях; конкретные TTL/таймауты единым конфигом и тестируемыми часами. Не коммитить heartbeat, пустые снимки, build cache, node_modules, virtualenv, токены и полные сессии. Не замораживать модель надолго ради диагностического архива.

Статус различает: связь с процессом, наблюдаемое действие, последний remote checkpoint, фактические проверки. Показывать repo/branch/SHA, notebook/attempt/model, phase/reason, свежесть наблюдения, возраст несохранённой работы, next action и срок. Unknown usage не равно нулевым затратам; tool calls и изменённые файлы не являются процентом готовности.

## 8. Восстановление и модели

Не раздувать enum десятками переходных состояний. Достаточно компактного lifecycle плюс `phase`, `reason_code`, `last_observed_at`, `next_action_at`, attempt generation и данные проверок. Потеря связи — явно наблюдаемая процедура сверки, не бесконечный немой UNKNOWN и не выдуманный RUNNING.

| Ошибка/событие | Поведение |
| --- | --- |
| Timeout launch или push | Проверить фактическую попытку/ref и сохранённый эффект; не дублировать вслепую |
| Notebook погиб | Новая попытка только этой части от подтверждённого Git checkpoint; завершённые соседи не перезапускаются |
| Heartbeat пропал | Сверить provider/lease, не считать смерть установленной по одному missed heartbeat |
| Исчерпан срок notebook | Сохранить код заранее; передать продолжение новой попытке |
| Временный 429/5xx модели | Ограниченный backoff с jitter или настроенный fallback, без бессмысленной замены VM |
| `free usage exceeded`/дневной лимит | Wrapper сохраняет/push/readback; записывает причину и запрос replacement/continuation; продолжает ту же часть из checkpoint, когда доступна модель |
| Общая квота исчерпана | Новая VM сама лимит не сбрасывает; настроенная альтернативная модель или явное waiting с условием повторной проверки, без фабрики одинаково падающих notebooks |
| GitHub token expired | Автоматический refresh до Git-операции, проверка неоднозначного push и ограниченный повтор |
| Supervisor недоступен | Буфер/доставка и локальный таймаут lease; по его истечении wrapper останавливает OpenCode и новые внешние действия |
| Старый worker ожил | Его ветку сохранить для диагностики, результат не принять как текущий; новые credentials не выдавать |
| Отмена | Прекратить новые задачи; отправить checkpoint/stop; отдельно подтвердить остановку процесса и освобождение ресурса |
| Перезапуск/restore supervisor | Восстановить DB, сверить Git/Kaggle и очередь coordinator, затем продолжить; не стартовать всё заново |
| Нераспознанная/неисправимая ошибка | Один общий диагностируемый failure path, bounded retry, сохранённый partial и конкретный handoff |

В Kaggle adapter stop и delete различаются. Основной stop — команда wrapper с локальным watchdog; provider stop применять только при реально поддерживаемой операции. Удаление notebook не называть недеструктивной отменой. Если stop не подтверждён, не объявлять ресурс свободным; показывать stop_pending/reconciliation с дальнейшим действием.

Модели выбираются из подключённых OpenCode providers (Zen/NVIDIA/GPT/другие), по явному ID или небольшому упорядоченному профилю. Нет классификации кода. Фактическая модель и причина переключения сохраняются. У общей квоты — общий cooldown; дополнительные ключи не считать независимыми лимитами без подтверждения. Платный резерв включается только в выбранном владельцем бюджете; сильная модель может использоваться для ответственных частей и финального контроля.

Бюджеты времени/стоимости/числа попыток и предел непродуктивных исправлений задаются на job; неизвестная стоимость указывается явно. Успех произвольного кода не гарантируется, но каждый завершённый путь даёт проверенный результат либо сохранённый partial с понятной причиной. Восстанавливается последний подтверждённый checkpoint, не магически все ещё не сохранённые байты.

## 9. Интеграция, CI и передача в ChatGPT

Проверки задаются из существующих project commands/CI, при необходимости центральным profile; они исполняются в подходящем окружении. Не требовать Docker/Android/Windows capabilities от любого Kaggle worker. Основной OpenCode выполняет конечную склейку и тесты на доступной инфраструктуре; недоступность инфраструктуры называется отдельно от дефекта кода.

Worker tests — предварительные. Итог подтверждается на объединённом SHA с baseline старых failures, точными командами, exit codes, test results и идентичностью окружения. Ноль запущенных тестов, skipped workflow, отсутствие checks, изменённый/удалённый набор тестов не превращаются автоматически в green. Изменение SHA требует свежей проверки.

GitHub App push/PR способен запускать существующие workflow; это не означает автоматическую корректность конкретного CI. Проверить фильтры до canary: checkpoint-ветки не должны неожиданно раскатывать приложение или создавать лавину проверок. Использовать существующую схему repo; при необходимости минимальное согласованное branch-filter изменение, не новый CI engine. Не применять глобальный skip-CI, который затем скрывает финальную проверку. Для DAEP не нужен self-hosted GitHub runner, webhook или `/opencode` через комментарии.

Один итоговый PR или обновляемый компактный result/handoff содержит задачу, repo/base/result SHA, решения, выбранные commits, команды/ошибки и конкретный следующий запрос. Логи доступны отдельно по ссылкам/хешам. Пакет должен читаться в новом ChatGPT через GitHub без доступа к прежнему окну; временная sandbox-ссылка не является единственным носителем.

`worker completed`, `code saved`, `integrated`, `verified`, `handoff_ready` — разные факты. Job success только после критериев исходной задачи, а не по фразе модели. Не делать merge/production deploy без соответствующего scope задачи.

## 10. Резервирование, хранение, ретроспектива

GitHub хранит код и checkpoints в ветках, а не operational dumps. Контролировать частоту commits; публиковать компактную историю результата и удалять временные ветки только после сохранённого итогового результата и установленного retention. Удаление ветки/squash не считать гарантией немедленного удаления исторических Git-объектов.

Runtime DB, конфигурация, handoff state и ограниченные traces живут вне checkout. Использовать согласованный SQLite backup в существующее внешнее хранилище, не копию на том же диске. Настройки bootstrap, версии пакета и способ восстановления credentials также нужны для restore. Нужен один путь резервирования, не новый storage-продукт. Конкретное хранилище и допустимое окно потери метаданных фиксируются перед live; отсутствие backup не выдаётся за промышленную готовность.

Один активный controller с автоматическим рестартом. Restore на другой машине предварительно исключает одновременное управление старым экземпляром; случайный новый generation ID сам по себе не решает two-active-controllers. Active-active HA не реализуется. Перед новой выдачей заданий reconcile Git/provider; уже подтверждённый remote код не теряется из-за отката DB, новые неподтверждённые метаданные имеют честно указанное окно потери.

Компактный итог строится из того же event log: результат, попытки, расходы/unknown, время, вмешательства, потерянная работа, проверки. По запросу export для сильной модели с выбранными failures, не весь бессрочный архив. Авторетроспектива может предлагать исправление; не создаёт автоматически десятки issues, не переписывает действующий controller и не ослабляет приёмку.

## 11. Реализация без расползания и приёмка

Не оценивать готовность наличием README/схем/зелёных unit-тестов. Собрать один вертикальный путь с надёжностью внутри, а не сначала большой framework:

1. Локальный supervisor/store/CLI + GitHub App mint/refresh + Git checkpoints; fake Kaggle для fault injection и тестовый OpenCode provider, без притворного live.
2. Глобальный вход OpenCode, реальный Kaggle wrapper и возврат событий в управляемого coordinator. Один canary, затем две действительно перекрывающиеся coding-попытки.
3. Потеря одного worker, восстановление из Git, интеграция, существующие сквозные проверки, один PR/handoff. Проверка другого проекта, max 1–4, restore.

Это один deliverable, не разрешение остановиться после пункта 1. Отсутствующий внешний доступ фиксируется точным blocker, но не блокирует независимую source-реализацию.

| Приёмка | Что нужно доказать |
| --- | --- |
| GitHub | Реальный clone точного SHA, push/readback, повтор после потерянного ACK, обновление токена, один PR без дублей |
| Распределённая работа | Две реальные независимые coding-части одновременно в Kaggle, события доступны до конца |
| Recovery | Падает один worker; продолжается только он, другой результат не теряется, stale результат не принят |
| Координатор | Закрывается/переподключается UI и перезапускается управляющий процесс; результаты вызывают продолжение интеграции, не остаются навсегда в очереди |
| Parallelism | Ручные 1–4/auto, общий предел и внешняя занятость; реальные две сессии не выдаются за подтверждённые четыре |
| Модельные сбои | Free-limit checkpoint/handoff, общий quota cooldown, fallback и исчерпание бюджета без бесконечного notebook churn |
| Проверки | Итоговый SHA соответствует реальному runtime/test result; нет CI/deploy storm от checkpoints |
| Переносимость | Второй проект без изменения ядра; сохраняемый читаемый ChatGPT handoff |
| Backup | Restore на чистом окружении с reconcile, без ручного составления списка jobs и повторного принятия commits |

Точное число тестов не является acceptance. Инъекция истечения token тестируется детерминированно; реальный mint/refresh/live long-run отмечаются раздельно. Нет доступа к модели/серверу — этот сценарий NOT_RUN, не PASS.
